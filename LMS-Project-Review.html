Project Overview
What was built and for whom

A production-grade, multi-tenant LMS SaaS where each customer (tenant) gets their own isolated data space, subdomain, and optionally a dedicated database. The platform supports four distinct user roles with different capabilities, a full course builder, 9-type quiz engine, billing/subscription management, and certificate issuance.

👥 User Roles
  • Super Admin — platform owner
  • Tenant Admin — school owner
  • Instructor — course creator
  • Student — learner
🏢 Multi-Tenancy
  • Subdomain-based tenant resolution
  • Shared DB (default) or dedicated DB per tenant
  • tenantId first in all compound indexes
  • Custom domain support
🔐 Auth & Security
  • JWT RS256 (asymmetric keys)
  • Access token: 15 min
  • Refresh token: 7 days, rotating
  • Silent refresh on 401 (failed-queue)
  • RBAC permissions per role

Key Architecture Rules
Never change these — they hold the system together
  • tenantId ALWAYS first in every compound MongoDB index — ensures tenant isolation at the query planner level.
  • All DB queries through Repository layer — no direct Mongoose calls inside services. Keeps data access testable and consistent.
  • Super Admin routes mounted BEFORE resolveTenant middleware — otherwise the middleware fails trying to find a tenant from the platform admin's requests.
  • Soft delete on all collections EXCEPT: Enrollment, Invoice, LessonProgress, CourseProgress, QuizAttempt — these are audit/financial records and must not be hidden from history.
  • Invoices are immutable — once created they are never edited, only marked paid/cancelled. A new invoice is created for corrections.
  • CommonJS throughout the backend — require() / module.exports only. No ES module syntax in apps/api.
  • JWT RS256 private + public keys live at apps/api/keys/ — never commit to Git. They are loaded at boot and used for all token signing/verification.
  • X-Tenant-Subdomain header is how every API request identifies which tenant it belongs to. Frontend attaches it from the cookie on every Axios request.

What's Next
Recommended steps to go from complete codebase to live production
1
Local Testing — Connect MongoDB & Smoke Test
Start MongoDB locally, seed a test tenant + users, run the API (npm run dev in Turborepo), and test all major flows: register → verify email → login → create course → enroll → complete → certificate. Use Postman or Insomnia for backend endpoints.
2
MongoDB Atlas — Production Database
Create a free M0 cluster on MongoDB Atlas, whitelist IPs, create a DB user, copy the connection string into environment variables. Enable Atlas Search if you want full-text course search later.
3
Deploy API — Render.com
Push apps/api to GitHub, create a new Web Service on Render, set root directory to apps/api, add all environment variables (MONGO_URI, JWT keys, REDIS_URL, SMTP config), and deploy. Add Redis via Render's Redis service or Redis Cloud.
4
Deploy Frontend — Vercel
Import the monorepo on Vercel, set root directory to apps/web, add NEXT_PUBLIC_API_URL pointing to the Render API URL, and deploy. Set up a custom domain if desired.
5
Optional Future Features
Stripe payment integration (replace manual billing), S3/Cloudflare R2 for file storage (replace local multer), email delivery via Resend or SendGrid (replace SMTP), video transcoding via Mux or Cloudflare Stream, analytics dashboard with real charts (Recharts/Chart.js), mobile app (React Native).
